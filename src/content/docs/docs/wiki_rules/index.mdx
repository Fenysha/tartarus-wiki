## Общие положения

Этот документ предназначен для тех, кто добавляет или редактирует материалы вики **Tartarus Project**.

Вики построена на **Astro + Starlight**. Основное содержимое хранится в Markdown/MDX-файлах, а структура каталогов, frontmatter и компоненты определяют то, как эти документы отображаются на сайте.

> **Важно:** для работы с содержимым вики не требуется изменять исходный код сайта. В большинстве случаев достаточно создать или отредактировать соответствующий `.md` или `.mdx` файл.


## 01 — Структура проекта

Основные документы вики находятся внутри:

```text
src/
└── content/
    └── docs/
```

Именно каталог `docs` является корнем содержимого документационной части сайта.

Внутри него создаётся иерархия разделов:

```text
docs/
├── index.mdx
├── lore/
│   ├── index.mdx
│   ├── history/
│   │   └── index.mdx
│   └── factions/
│       └── index.mdx
│
├── protocols/
│   ├── index.mdx
│   └── security/
│       └── index.mdx
│
└── technical/
    └── index.mdx
```

Название и глубина каталогов не ограничены. Структура должна отражать логическую организацию материалов.

Например:

```text
docs/
├── lore/
├── protocols/
├── characters/
├── locations/
└── technical/
```

означает, что каждый из этих каталогов представляет отдельный раздел документации.

## 02 — Файл `index`

В Starlight файл `index.md` или `index.mdx` обычно используется как главная страница соответствующего каталога.

Например:

```text
docs/
└── lore/
    ├── index.mdx
    └── history/
        └── index.mdx
```

В данном случае:

```text
lore/index.mdx
```

представляет страницу раздела `lore`, а:

```text
lore/history/index.mdx
```

— страницу подраздела `history`.

Поэтому структура каталогов может одновременно использоваться как структура навигации.

## 03 — Markdown и MDX

Вики поддерживает два основных формата документов.

### `.md`

Обычный Markdown.

Используется для документов, которым достаточно стандартного форматирования:

```md
---
title: История
---

# История

Текст документа.

## Первый период

Описание событий.
```

### `.mdx`

Markdown с возможностью использовать React/Astro-компоненты и другой расширенный синтаксис.
Подробне о компонентах, [тут](wiki_rules/components)


Например:

```mdx
---
title: Технический документ
---

import DataTable from '@components/DataTable.astro';

# Технический документ

Описание.

<DataTable
    rows={[
        { label: 'Статус', value: 'Активен' },
        { label: 'Версия', value: '1.0' },
    ]}
/>
```

Если документ использует компоненты вики, рекомендуется использовать `.mdx`.

<DataTable
labelHeader="Формат"
valueHeader="Использование"
rows={[
{ label: '.md', value: 'Обычный Markdown-документ' },
{ label: '.mdx', value: 'Markdown с компонентами и расширениями' },
]}
/>

## 04 — Frontmatter

В начале документа располагается блок метаданных, называемый **frontmatter**.

Он заключён между двумя строками `---`:

```md
---
title: Название документа
description: Краткое описание
---
```

Минимально рекомендуется указывать `title`.

Например:

```md
---
title: Общие правила
---
```

Описание можно использовать для краткой характеристики документа:

```md
---
title: Общие правила
description: Основные правила игрового сервера
---
```

Frontmatter располагается **до любого другого содержимого**.

Нельзя помещать перед ним обычный текст или импорт компонента.

Правильно:

```mdx
---
title: Документ
---

import DataTable from '@components/DataTable.astro';
```

Неправильно:

```mdx
import DataTable from '@components/DataTable.astro';

---
title: Документ
---
```

## 05 — Заголовки

Иерархия заголовков Markdown определяет структуру самого документа.

Основной заголовок страницы обычно задаётся через `title`:

```md
---
title: Общие правила
---
```

После него используются заголовки второго уровня:

```md
## Общие положения

## Ограничения

## Дополнительная информация
```

Подразделы оформляются заголовками третьего уровня:

```md
## Общие положения

### Основной принцип

### Исключения
```

Не рекомендуется перескакивать через уровни:

```md
## Раздел

#### Подраздел
```

Используйте последовательную структуру:

```md
## Раздел

### Подраздел
```

## 06 — Внутренние ссылки

Для ссылок между страницами вики следует использовать относительные пути.

Например, если существует:

```text
docs/
├── lore/
│   ├── history/
│   │   └── index.mdx
│   └── factions/
│       └── index.mdx
```

из страницы `lore/index.mdx` можно ссылаться на подразделы:

```md
[История](history/)
[Фракции](factions/)
```

Если необходимо подняться на уровень выше:

```md
[Главная страница](../)
```

Не следует использовать полный адрес сайта:

```md
[История](https://example.com/lore/history/)
```

Относительные ссылки позволяют менять домен, способ размещения и структуру хостинга без необходимости переписывать все ссылки в документах.

## 07 — Ссылки на внешние ресурсы

Для внешних сайтов используются обычные Markdown-ссылки:

```md
[GitHub](https://github.com/)
```

Внутренние и внешние ссылки следует различать:

```md
[История](../history/)
```

— внутренняя ссылка.

```md
[GitHub](https://github.com/)
```

— внешняя ссылка.

## 08 — Компоненты

Компоненты позволяют создавать элементы интерфейса, которых нет в стандартном Markdown.

Компоненты находятся в:

```text
src/
└── components/
```

Например:

```text
src/
└── components/
    ├── DataTable.astro
    ├── DocumentHeader.astro
    └── ImagePanel.astro
```

Для использования компонента его необходимо импортировать:

```mdx
import DataTable from '@components/DataTable.astro';
```

После этого компонент можно использовать в документе:

```mdx
<DataTable
    rows={[
        { label: 'Статус', value: 'Активен' },
        { label: 'Тип', value: 'Архивный' },
    ]}
/>
```

### Почему используется `@components`

Alias `@components` указывает на каталог:

```text
src/components/
```

Поэтому вместо длинного относительного пути:

```md
../../../../components/DataTable.astro
```

используется:

```md
@components/DataTable.astro
```

Это особенно важно для документов, расположенных глубоко в структуре каталогов.

## 09 — Использование компонентов

Перед использованием компонента необходимо проверить его параметры.

Например, `DataTable` принимает список строк:

```mdx
<DataTable
    rows={[
        { label: 'Параметр', value: 'Значение' },
        { label: 'Статус', value: 'Активен' },
    ]}
/>
```

`DocumentHeader` используется для отображения технических характеристик документа:

```mdx
<DocumentHeader
    security="EKHU"
    threat="LOW"
    status="OPEN"
/>
```

Компоненты должны использоваться по назначению.

Если обычный Markdown решает задачу достаточно хорошо, не следует создавать компонент только ради визуального эффекта.

## 10 — Изображения

Изображения могут размещаться в публичной директории проекта, например:

```text
public/
└── images/
    ├── archive/
    └── locations/
```

После этого они доступны по пути:

```text
/images/archive/example.jpg
```

В простом Markdown:

```md
![Описание изображения](/images/archive/example.jpg)
```

Если требуется оформление архивного изображения, можно использовать `ImagePanel`:

```mdx
<ImagePanel
    src="/images/archive/example.jpg"
    alt="Описание изображения"
    caption="Описание архивного материала"
    reference="IMG-0001"
    source="ARCHIVE"
/>
```

Параметр `alt` предназначен для описания изображения и важен для доступности.

`caption` используется как видимая подпись.

`reference` задаёт идентификатор архивной записи.

`source` указывает источник материала.

## 11 — Таблицы

Для простых таблиц можно использовать стандартный Markdown:

```md
| Параметр | Значение |
|----------|----------|
| Статус   | Активен  |
| Версия   | 1.0      |
```

Для таблиц, которые должны соответствовать визуальному стилю вики, используется `DataTable`.

```mdx
<DataTable
    labelHeader="Параметр"
    valueHeader="Значение"
    rows={[
        { label: 'Статус', value: 'Активен' },
        { label: 'Версия', value: '1.0' },
    ]}
/>
```

`DataTable` особенно удобен для:

* технических характеристик;
* классификаций;
* списков параметров;
* кратких сводок;
* структурированных данных.

Не рекомендуется использовать таблицу для больших объёмов обычного текста.

## 12 — Списки

Для перечислений используется стандартный Markdown:

```md
- Первый пункт
- Второй пункт
- Третий пункт
```

Нумерованные списки:

```md
1. Первый этап
2. Второй этап
3. Третий этап
```

Вложенные списки:

```md
- Основной пункт
  - Подпункт
  - Подпункт
```

## 13 — Цитаты и предупреждения

Для выделения важных замечаний используется Markdown blockquote:

```md
> **Важно:** это правило применяется ко всем документам.
```

Не следует использовать предупреждения вместо обычного текста.

Выделение должно сообщать действительно важную информацию: ограничение, исключение, примечание или особое условие.

## 14 — Именование файлов

Для файлов рекомендуется использовать латинские символы и `kebab-case`.

Хорошие примеры:

```text
general-rules.mdx
server-history.mdx
security-protocol.md
character-background.mdx
```

Не рекомендуется:

```text
Общие правила.md
General Rules.md
документ1.md
document_final_final2.md
```

Имя файла должно описывать его содержимое.

## 15 — Организация каталогов

Каталог следует создавать тогда, когда у него есть логическое назначение.

Например:

```text
docs/
├── lore/
│   ├── history/
│   ├── factions/
│   └── locations/
│
├── protocols/
│   ├── security/
│   └── administration/
│
└── technical/
```

Не следует создавать глубокую иерархию без необходимости:

```text
docs/
└── lore/
    └── miscellaneous/
        └── other/
            └── additional/
                └── document/
```

Каждый уровень структуры должен отвечать на вопрос:

> «Почему этот документ находится именно здесь?»

## 16 — Навигация

Starlight может использовать структуру каталогов для построения навигации, однако отображение страниц в боковой панели также зависит от конфигурации сайта.

Поэтому наличие файла в `src/content/docs/` ещё не означает, что он автоматически окажется в нужном месте навигации.

При добавлении нового крупного раздела может потребоваться изменение конфигурации sidebar.

Структура содержимого и структура навигации — связанные, но не идентичные вещи.

## 17 — Логические пути

Для архивной системы рекомендуется использовать логические пути документов:

```text
/docs/lore/
/docs/lore/history/
/docs/protocols/security/
```

Они не должны содержать домен сайта:

```text
https://example.com/docs/lore/
```

Логический путь описывает положение документа внутри информационной системы, а не способ доступа к сайту.

Это позволяет в будущем изменить хостинг, домен или способ хранения данных без изменения самих документов.

## 18 — Рекомендуемая структура документа

Для большинства содержательных страниц рекомендуется следующая структура:

```text
Frontmatter

Техническая шапка
        ↓
Краткая сводка
        ↓
Основная информация
        ↓
Подразделы
        ↓
Таблицы / изображения / дополнительные материалы
        ↓
Примечания
```

Пример:

```mdx
---
title: Название документа
description: Краткое описание
---

import DocumentHeader from '@components/DocumentHeader.astro';
import DataTable from '@components/DataTable.astro';

<DocumentHeader
    security="EKHU"
    threat="LOW"
    status="OPEN"
/>

## Краткая сводка

Краткое описание содержимого документа.

<DataTable
    rows={[
        { label: 'Статус', value: 'Активен' },
        { label: 'Тип', value: 'Архивный документ' },
    ]}
/>

## Основная информация

Основное содержимое документа.

### Дополнительные сведения

Дополнительная информация.

## Примечания

Дополнительные замечания и ссылки.
```

## Главное

Вики строится вокруг трёх основных уровней:

```text
СОДЕРЖИМОЕ
    ↓
Markdown / MDX

СТРУКТУРА
    ↓
Каталоги / файлы / sidebar

ПРЕДСТАВЛЕНИЕ
    ↓
Astro / Starlight / компоненты
```

**Markdown и MDX отвечают за содержание.**

**Каталоги и конфигурация Starlight отвечают за организацию.**

**Astro-компоненты отвечают за расширенное представление информации.**

При добавлении нового материала желательно изменять только тот уровень, который действительно требуется.

Не стоит создавать Astro-компонент там, где достаточно Markdown, и не стоит менять структуру проекта ради одного небольшого документа.

Вики должна оставаться простой для добавления новых материалов и предсказуемой для тех, кто будет поддерживать её в дальнейшем.
